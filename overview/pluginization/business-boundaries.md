# 从业务变化确定模块边界

论坛增加一条审核规则，需要同时调整主题状态、正文可见性和相关查询。若这次修改必须穿过多个团队维护的“模型库”“服务库”和“控制器库”，团队面对的问题首先是规则归谁维护。文件已经分类，并不意味着业务变化已有明确的负责人。

在 Zongsoft 中，可以先用一个完整的业务动作寻找边界，再选择程序集、插件清单和部署包来承载它。本篇以现有论坛模块为依据，讨论边界判断；文中的拆分建议是设计方法，不是框架要求的固定目录模板。

## 跟踪一次修改会经过哪些规则

论坛中的“批准主题”不只是把一个布尔字段写成真。[ThreadService.Approve](https://github.com/Zongsoft/discussions/blob/main/src/Services/ThreadService.cs) 将主题编号、尚未批准和版主资格组成更新条件，并关联更新正文的批准状态。如果两个团队分别拥有主题审核和正文审核，就必须共同维护这次动作的一致语义。

创建主题还会涉及正文存储和作者统计。当前服务在事务中完成数据插入与统计更新，并由正文处理逻辑应对文件写入与数据库操作之间的失败，详见[事务与一致性](../../framework/data/transactions.md)。这些关系为模块划分提供了具体证据：哪些数据总是一起变化，哪些失败必须一起处理，哪些规则需要由同一处解释。

可以挑选最近几次需求变更，记录修改过的规则、数据和入口。经常一起修改、需要共同验收的部分，适合先放在同一业务边界内。单纯因为两个类型都包含“用户”二字就把它们集中到一个共享模块，反而可能把登录身份、论坛作者统计和客户资料混在一起。

## 四种边界分别决定什么

Zongsoft 为不同阶段提供不同组织手段。先明确每种手段负责什么，才能避免一次拆分同时承担过多目标。

| 边界 | 决定的问题 | 论坛中的落点 |
| --- | --- | --- |
| 应用模块 | 业务身份、模块服务及事件如何组织 | [Module](https://github.com/Zongsoft/discussions/blob/main/src/Module.cs) 定义 Discussions 模块及其访问器 |
| 程序集 | 哪些类型一起编译，允许引用哪些依赖 | 领域库与 [Discussions.Web](https://github.com/Zongsoft/discussions/tree/main/src/api) 分开编译 |
| 插件 | 运行时加载哪些程序集，向哪里贡献对象 | 领域清单与 Web 清单分别声明装配关系 |
| 部署方案 | 交付哪些版本、配置和资源 | `.deploy` 文件描述需要进入运行目录的产物 |

[应用模块](https://github.com/Zongsoft/framework/blob/main/Zongsoft.Core/src/Services/IApplicationModule.cs)与插件没有自动的一一对应关系。论坛的 Web 清单依赖领域插件，两个插件一起提供论坛的使用入口。拆出 Web 程序集可以限制协议依赖，并不要求再创建一个“Web 业务模块”。具体概念见[模块、服务与提供者](../concepts.md#module-service-provider)。

## 完整性应覆盖规则和交付资源

一个业务模块的维护责任应覆盖实现规则所需的模型、服务、映射、选项和资源。新增字段若只修改 C# 类型，却遗漏映射和数据库脚本，编译成功的模块仍可能无法运行。边界是否完整，要通过实际交付来判断。

这不要求所有文件进入同一个程序集。论坛的 [Web 部署文件](https://github.com/Zongsoft/discussions/blob/main/src/api/Zongsoft.Discussions.Web.deploy)另外交付控制器插件和表格模板，领域[部署文件](https://github.com/Zongsoft/discussions/blob/main/src/Zongsoft.Discussions.deploy)交付领域清单、选项和映射。维护者需要知道两者如何组成可用功能，而不是把“分文件发布”理解成“彼此无需兼容”。

边界内可以继续分层。业务服务负责审核规则，控制器负责 HTTP 适配，数据访问负责持久化；这些职责明确以后，一次审核规则调整才有可能主要落在服务及其验证用例中。进一步讨论见[跨宿主复用](host-independent-business.md)。

## 用候选拆分检验边界

假设要为论坛增加外部搜索索引，这是一个待设计的能力。它有独立的查询技术和重建流程，可以作为独立插件的候选；但需要先决定索引延迟是否可以接受、主题隐藏后多久必须不可检索、删除如何传播、故障时如何恢复。

如果产品要求内容隐藏立即生效，搜索结果就不能仅凭旧索引决定可见性。可以在返回结果前核验业务状态，或设计满足时效要求的更新机制。此时论坛拥有可见性规则，索引插件承担搜索实现；“拆开了”不会替双方完成这个约定。

相反，若打算把“批准主题”和“批准主题正文”拆成两个插件，却无法给出独立的使用场景、失败处理和发布节奏，那么新增的协作成本很可能超过收益。可以保留内部类型分工，暂时不增加独立装配边界。

## 服务域需要配合工程约束

模块服务容器有助于组织服务查找，不能阻止同进程代码引用其他模块实现或访问其数据库。若团队约定只能通过公开业务契约协作，还应在项目引用审查、接口评审和测试中落实约束。[核心类库](https://github.com/Zongsoft/framework/tree/main/Zongsoft.Core)适合承载通用契约，特定产品的跨模块契约则应由产品团队明确归属，避免把所有共享类型都放进一个无限增长的公共库。

{% hint style="info" %}
模块划分可以随理解加深而调整。对于只有一个部署方案、少量规则且维护周期短的应用，先保持简单结构更合适；出现重复变化、团队协作或独立交付需求时，再引入相应边界。
{% endhint %}

评审一个候选模块时，尝试说明它维护的业务规则、允许外部使用的入口、依赖缺失时的行为，以及替换它需要共同验证哪些产物。如果只能列出目录名，边界还需要继续推敲。下一篇从这些入口出发，讨论[如何让业务能力跨宿主复用](host-independent-business.md)。
