# 把扩展点设计成协作契约

一个插件能够被加载，只说明它进入了运行环境。要让另一个团队为它增加能力，还需要说明对象挂在哪里、遵守什么接口、何时调用，以及失败后由谁负责。扩展点的价值取决于这些约定能否让双方独立工作。

Zongsoft 的插件树把装配位置显式化，服务容器提供能力查找。设计者需要为这些机制补上业务语义。本篇从论坛的真实过滤器挂载出发，讨论如何维护一份可供其他插件使用的契约。

## 从一个现有扩展点读出两方责任

论坛的 [Zongsoft.Discussions.plugin](https://github.com/Zongsoft/discussions/blob/main/src/Zongsoft.Discussions.plugin)在 `/Workbench/Modules` 下引用已有模块实例，并暴露访问器的过滤器集合。随后，它把两个过滤器挂到 `/Workbench/Modules/Discussions/Accessor/Filters`。

这段装配关系包含两种责任：模块一侧提供可以被扩展的集合，过滤器一侧提供符合要求的对象。清单中的 `expose` 连接现有成员，`object` 的 `type` 描述需要构建的实例。具体 XML 见[插件文件与加载](../../framework/plugins/plugin-file.md)。

路径也只是契约的一部分。现有过滤器还按模型匹配，挂载成功不意味着所有查询都会执行它。外部插件若继续向这个集合贡献对象，必须理解匹配条件、处理阶段和对象生命周期，不能只复制路径字符串。

## 选择协作方式时先明确完成条件

| 协作需要 | 可以采用的方式 | 需要写清楚的约定 |
| --- | --- | --- |
| 调用方必须取得本次操作结果 | 通过明确契约调用服务 | 输入、结果、权限、超时及失败语义 |
| 能力拥有者允许别人加入处理步骤 | 向扩展点贡献过滤器、处理器或驱动 | 适用范围、顺序、共享状态和异常处理 |
| 一个事实发生后通知多个关注方 | 定义事件及处理方式 | 触发时机、载荷、订阅者失败的影响 |
| 工作需要跨进程或在故障后继续投递 | 采用消息机制并安排持久化策略 | 确认、重试、重复处理及恢复责任 |

这些方式可以组合。例如业务操作通过服务完成，提交后再安排外部索引更新。但一个必须成功才能确认交易的步骤，不应仅因为希望“解耦”就改成没有完成约定的通知。事件减少了对具体订阅者的引用，也会把一部分依赖转移到事件语义和运行诊断上。

{% hint style="info" %}
当前论坛的 [EventRegistry](https://github.com/Zongsoft/discussions/blob/main/src/Module.cs)尚未定义具体业务事件。插件清单暴露 `Events` 并不表示发帖或审核已经发布事件，更不表示已经可靠投递到消息队列。新增这类能力仍需要完整实现，见[事件](../../framework/core/components/events.md)。
{% endhint %}

## 为扩展点写一份使用说明

假设产品准备允许第三方增加审核后的索引处理器，评审时至少需要形成下列说明。这是扩展设计建议，不是当前论坛已有的扩展 API。

- **所有者与入口**：由谁维护扩展点，贡献插件需要依赖哪个插件，目标集合接收什么契约。
- **输入与适用范围**：提供已提交的业务标识还是可变对象，如何标识站点，哪些动作会触发处理。
- **顺序与并发**：多个处理器是否有先后关系，是否并发执行，能否重复调用。不要把文件排列顺序当成业务顺序保证。
- **失败与生命周期**：异常是否影响主操作，谁记录和重试，停机时是否等待在途任务。
- **兼容与验证**：如何处理新增字段，旧插件能否继续工作，缺少处理器时业务是否仍然可用。

扩展点公开可变对象越多，外部插件越容易依赖内部细节。对于需要长期兼容的扩展，宜提供与动作目的相称的输入和输出，避免为了方便把整个服务容器、数据库访问器和内部对象图都变成公共协议。

## 插件依赖与项目引用要一起审查

论坛的 [Web 清单](https://github.com/Zongsoft/discussions/blob/main/src/api/Zongsoft.Discussions.Web.plugin)声明依赖领域插件。程序集引用负责让类型可编译，清单依赖负责运行时装配要求，部署方案负责把文件带到目标环境。三者都应与真实调用关系一致；清单中声明名称不会自动下载 NuGet 包。

如果两个业务插件需要互相引用内部服务，并在启动时等待对方构建对象，先检查协作职责能否重新归属。可以提取稳定的公开契约，或让一个负责完整流程的上层组件协调双方。需要立即结果的依赖仍应明确保留，不能仅把它改成字符串服务名就宣称依赖消失。

模块内服务优先解析和共享服务回退的行为见[应用模型](../../framework/plugins/application-model.md)。这种查找机制有助于选择实现，但消费者仍要知道自己依赖哪个能力、实现来自哪里，以及找不到时如何处理。

## 让名称能帮助定位，但不混淆名称域

故障记录中只出现一个 `Discussions`，读者可能不知道它指模块、插件还是连接配置。为扩展写说明时，应同时给出名称的类别及所属范围，避免让团队靠字符串相同来猜测关系。

论坛提供了直观例子：Web 插件名为 `Zongsoft.Discussions.Web`，它依赖 `Zongsoft.Discussions` 插件；业务模块名为 `Discussions`；`PostFilter` 则是访问器过滤器集合下的构件名。它们分别参与插件依赖、模块查找和树节点定位，不能互相替代。新增公开路径或服务别名时，也应说明所有者与适用范围，并维护已有消费者使用的名称。

## 验证装配结果，也验证业务效果

扩展点的测试应覆盖“插件已经加载，但扩展没有按预期工作”的情况。例如模型不匹配、重复注册、缺少目标节点、处理器异常、顺序变化，以及同一实例并发处理多次调用。只验证类型能构建，会遗漏这些协作问题。

对于需要可靠通知的扩展，还要验证数据库提交与消息发送之间的失败窗口。可根据一致性需求设计持久化待发送记录、补偿或对账机制；这些属于应用方案，不能从“框架支持事件”推断已经自动获得。具体投递边界见[消息概念](../../framework/messaging/concepts.md)。

契约清楚以后，维护者才能判断新插件是否兼容、缺少可选插件是否允许启动，以及某次失败由谁接手。下一篇把这些约定带到[渐进改造与交付](evolutionary-delivery.md)，检验它们能否支撑实际发布。
